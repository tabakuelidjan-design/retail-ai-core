# Notes d'audit — Nordla Core / Identity / Tenant / Security / Sync (agent lecture seule, core-p0 ebff21e ; échantillonnage partiel, incertitudes signalées)
- **Fait structurel : il n'y a PAS de serveur « Core » unifié autonome.** `createCoreHttp` (src/core-pilot/http.js:39) n'est monté que DANS le serveur China Sourcing (src/sourcing/server/index.js:22-29, 52-67) ; routes /api/core/* n'existent que là où Sourcing tourne. service-start.js : core (planificateur de synchro Shopify), finance, analytics, core-once, sourcing ; ni core-pilot, ni growth, ni procurement (monté via le serveur sourcing) ; growth a son serveur (src/growth/server/serve.js).
- Registre de modules / nav : identité `MODULES` = finance, analytics, growth, sourcing (src/identity/modules.js:6-11, sans statut) ; la nav UI = fonction runtime `modules()` (http.js:43-64) servie par GET /api/core/modules → `{key,label,state,detail,offline}` ; états FR : DISPONIBLE, LECTURE SEULE, LIMITÉ, À APPROUVER, À VÉRIFIER, BLOQUÉ, NON RACCORDÉ, NON CONFIGURÉ ; pas d'énumération opérationnel/partiel/indisponible (équivalence : DISPONIBLE = opérationnel ; LIMITÉ/LECTURE SEULE/À APPROUVER/À VÉRIFIER = partiel ; NON RACCORDÉ/NON CONFIGURÉ/BLOQUÉ = indisponible). Client : STATE_TONE nordla-view.js:~33 ; MODULE_META (core, sourcing, finance, procurement, analytics, branding, marketing, creative). La ligne Sourcing est codée en dur 'DISPONIBLE' (http.js:~55).
- core-pilot : routes sous l'autorisation /api du serveur Sourcing ; journal de décisions JSONL chaîné par hachage (verrou, datasync) ; marque approuvée (0600), campagnes, créations ; config config/merchants/<id>/core-decision.json ; séparation = un serveur par marchand (MERCHANT_MISMATCH) ; rôles : analyser OWNER|ADMIN|COLLABORATOR ; approbateurs selon required_approval (NONE: O/A/C ; MANAGER: O/A ; OWNER) ; branding.approve / campaign.decide / validation visuelle = OWNER ; **mode local : tout porteur du jeton est OWNER (journalisé LOCAL_TOKEN)**.
- « Guardian / Validations » : pas de module ainsi nommé dans ce groupe ; le garde-fou = decideHuman (runtime.js) avec rejet des approbateurs machine (ledger.js MACHINE_APPROVERS) ; pending-approvals.js est EN LECTURE SEULE (liste les décisions Core sans décision humaine et les BC Achats en PENDING_APPROVAL) ; garde de marque : src/branding/guardian.js (non audité ici) ; ask/analyse ne sont pas soumis à approbation mais journalisent ANALYSED et n'exécutent rien (executes_nothing).
- IA externe : aucune dans core-pilot (ask.js « No model ») ; campaign.js ne fait que vérifier la présence des variables ALIBABA_MODEL_STUDIO_*.
- Journal : ANALYSED, HUMAN_DECISION, RESULT avec acteur (user id + rôle, pas d'e-mail).
- deployment-guard.js:15-21 : refuse un journal hors RAILWAY_VOLUME_MOUNT_PATH seulement si une variable RAILWAY_* existe ; hors Railway = « l'opérateur porte les garanties » ; ne voit pas un second service écrivain ; verrou mono-écrivain par fichier.
- core-resilience : taxonomie d'erreurs pure ; adapters/domains.js importe AlibabaProviderError (couplage avec marketing-creative) ; aucun réseau.
- identity : sessions via GoTrue ; jeton opaque 32 octets, SHA-256 seul stocké (app_sessions) ; inactif 2 h, absolu ≤ 12 h ; membership et droits de module relus À CHAQUE requête ; LOGIN_FAILED unique côté public ; rate limits en base ; rôles OWNER/ADMIN/COLLABORATOR/VIEWER/ACCOUNTANT ; un service = un marchand + un module ; le module 'sourcing' exige la migration 20261015093000 (migrations-pending, NON appliquée ; incertain : contrainte de module_entitlements).
- tenant : source unique = env NORDLA_MERCHANT_ID ; source 'session' réservée non implémentée ; connectors.js.
- security : createHttpSecurity (CSRF, cookies, allow-list hôte/origine exacte, CSP, normalisation du temps de login, limites de corps, redaction by key/value) ; **la protection dépend de chaque serveur qui la câble** ; seul Sourcing hébergé confirmé câblé dans ce groupe.
- supabase/client.js : client PostgREST avec la clé SERVICE ROLE (contourne RLS) ⇒ l'isolation des marchands repose sur le code applicatif.
- sync : planificateur → src/sync/index.js (catalog, inventory, cost, orders, all) ; write-guard.js = garde tenant (liste blanche de tables, merchant_id obligatoire, mises à jour scopées, DELETE/RPC refusés ; lectures non filtrées au garde) ; réseau : Shopify Admin GraphQL + OAuth (données entrantes) ; risque : history.js:17 duplique l'appel OAuth.
- socle-decision : pur, en mémoire, déterministe, sans LLM ; SocleStore par merchantId ; persistance seulement par rejeu du journal core-pilot.
- Migrations : RLS activé sur de nombreuses tables mais **aucun `create policy` dans supabase/migrations** (= refus total anon/authenticated ; l'accès ne marche que par la clé service role) ; migrations-pending (NON appliquées) 20261015091000 : politiques RESTRICTIVES (nordla_deny_anon, nordla_tenant_guard) qui « n'ouvrent rien », tables integration_*, sourcing_cases, tables procurement, correctif search_path fin_* ; à vérifier : NOT NULL des tables merchant_id_gap.
- NORDLA-CANONICAL-ARCHITECTURE.md = document de conception, pas du code : revendique des capacités (validations/politiques du Socle, Centre des connexions) que le code ne couvre que partiellement.
- Risques transversaux : clé service role partout + isolation applicative + aucune politique RLS active ; durabilité du journal = vérification du volume ; mode jeton local = OWNER ; aucune sortie d'IA/clients trouvée dans ce groupe (seulement Shopify et Supabase).
