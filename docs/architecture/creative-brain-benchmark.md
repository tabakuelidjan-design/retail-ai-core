# Creative Brain benchmark 001 — the live runner

Status: wired and tested with fake ports. **Nothing has been run live.** `scripts/run-creative-brain-benchmark.mjs` is the only entry point; the logic is in `src/creative-brain-benchmark/` (provider-agnostic: every model, the image provider, the vision critic and the Brand Guardian are ports) and `src/marketing-creative/alibaba/qwen-brain-port.js` (the one place that names the provider).

## What it is
A fresh benchmark from the original brief and the real Samsung Galaxy A17 source asset, in a NEW private directory (`NORDLA_PRIVATE_DIR/creative-brain-benchmark-001`, default `~/nordla-private/creative-brain-benchmark-001`). It is not Candidate 4. It reads no earlier candidate, critique, direction or owner review (a test greps the sources), passes no reference image, and refuses an output directory that is the earlier run. Manual creative steering: none.

## Execution graph
```
OBSERVE → FRAME → IDEATE → SELECT CONCEPT → ART DIRECT → COMPOSE → SCENE → PRODUCTION STRATEGY      (Creative Brain, text port)
   → environment image (text-only scene request with the reserved integration zone)                    (image port)
   → deterministic product-preserving composite → Preflight → Fidelity → Brand Guardian                (runtime and gates)
   → execution critic (14 dimensions) + concept critic (6 dimensions)                                  (vision port, only if every gate passed)
   → recovery diagnosis → [RECONCEPT only: new concept → its single candidate → critics] → STOP for owner review
```
The relational composition is tried first; a preset is used only as a recorded `PRESET_FALLBACK` with its reason.

## Bounds
2 concept rounds in total (planning and recovery share them), 3 concepts per round, 1 production candidate per selected concept, 1 recovery action. Only a `RECONCEPT` is executed (it brings a new concept, which gets its own single candidate). A `REFINE` or `RECOMPOSE` decision is recorded as a recommendation and not executed: executing it would be a second candidate for the same concept.

## Cost and calls (worst case)
Text: 1 framing + 2 per concept round + 2 per planned candidate = 9. Images: 2. Vision: 2 critics × 2 candidates = 4. Total 15 calls. Each text call is bounded by construction (input refused above 12 000 estimated tokens before the network, output capped at 4 000 tokens, thinking off, no retry); the cost is computed from the lane's own price table (USD treated as EUR, which over-estimates). Worst case about EUR 0.57, spend guard at EUR 0.60, hard ceiling EUR 1.00 (the benchmark refuses to start above it).

## Modes
- `--check`: no network. Credentials (names only), output path new and writable, no earlier record or lock, asset hash, Brain contracts, capabilities, local segmentation dry-run, first instruction built from the brief only, worst-case cost.
- `--explain`: offline, read-only; the chain, the provider calls and the stop reason from the stored evidence.
- `--live --confirm-creative-brain-benchmark`: re-runs the checks, takes the exclusive lock (never released by code), then executes. No automatic retry.

## Result states
`BLOCKED`, `TECHNICAL_FAIL`, `TECHNICALLY_VALID_BUT_CREATIVELY_INSUFFICIENT`, `READY_FOR_OWNER_REVIEW`. Never a plain PASS; `OWNER_APPROVAL` is always `PENDING`; an unjudged candidate is never ready.

## Known risks
- The Brain sees only the names of the brand expression sections; the brand's "don't" lists are enforced afterwards by the existing check on the scene request, which stops the run before the image call (after the Brain stages were paid for).
- The prompts have never met a real model; a non-conforming answer stops the run at that stage (BLOCKED, recorded, no retry).

## Final state and failures
The final state is the state of the last candidate that exists; a failure while preparing the single recovery is recorded (`error`, `final.stopped_early`) and does not hide a candidate the owner can review. With no candidate the final state is `BLOCKED`. A candidate stopped before the image call is `BLOCKED`; one stopped after the image was paid for (or by Preflight, Fidelity or the Brand Guardian) is `TECHNICAL_FAIL`, and no critic is paid for.

## Tests and mutation
`test/creative-brain-benchmark.test.js` (23 runner tests: no network in `--check`, no leakage of earlier candidates or the owner reference, stage order, relational composition before a recorded preset fallback, substitute product refused, product preservation, bounded recovery, RECONCEPT from the concept stage, live lock, cost cap, evidence, owner never auto-approved, no secret in the output) plus `BR-9` for the round budget. 28 mutations of the runner, the bounded Brain rounds, the Brain port and the store: all killed.

## Incident 1: NO_LAYOUT_RECIPE_FOR_THE_SPATIAL_INTENT (first live attempt, cost EUR 0.0369, no image)
The Brain produced a valid plan and synthesized a recipe (dominant product anchored to the end, text beside it). Solved against the real approved words in the real fonts, that first recipe failed (`TEXT_DOES_NOT_FIT`, supporting claim, `TOO_MANY_LINES`: a one-line claim needs a slot of at least 57.5% of the usable width, the first text column was 40%). The preset fallback then had nothing for an END-anchored intent, and the record kept only the preset's reason. Root cause: **RECIPE_SYNTHESIZER_CAPABILITY_LIMIT** (the synthesizer fixed one set of proportions without regard to the words), made opaque by a reporting defect. Fix: a plan now yields a deterministic LADDER of recipes (`synthesizeRecipeLadder`): every rung keeps every relation of the plan and flexes only the text proportion, bounded by a dominance-by-area rule (a dominant product keeps at least 2.5 times the area of the largest text slot). The runtime tries the rungs in order against the real texts before any preset; a failure records every rung with the solver's own reasons, then the preset attempt and its reason (`NO_EXECUTABLE_LAYOUT_FOR_THE_COMPOSITION`). The stored plan of the incident now lays out at rung 7 (product 36.6% of the width, full 80% height, text column 57.5%).

## Incident 2: ENVIRONMENT_NOT_EMPTY (second live attempt, cost EUR 0.1048, one image, no PNG)
Concept `cnc_38416aeef…` (two pairs of hands handing over the case across a shop counter). The scene request was correct: hands "in the foreground, at the edges of the frame", a worn wood counter, and a reserved zone "completely calm and empty... nothing stands on it, nothing crosses it". The provider drew the two hands at the CENTRE of the frame, inside the zone where the product is placed (about 20 % object structure in the zone), on a strongly grained wood counter, and a sign with lettering and a logo glyph at the right edge. Verdict: the REFUSAL WAS RIGHT (the integration zone was occupied: provider scene non-compliance), and the gate also had a legacy defect: it counted wood grain as failure (pure wood bands measured 9-27 % fine edges), so any realistic material under the product would have been refused.
Fix (generic): the decision is now taken at OBJECT scale (`zoneObjectStructure`: luma averaged over blocks of about 1.5 % of the canvas width; a step between neighbouring blocks above 16 levels is structure; limit 2.5 % of the zone). Grain averages out; objects, hands, lettering and logos survive. The pixel-scale edge share is still measured and reported, but no longer decides. Calibration on every real environment we hold: phone on a stone slab 10.9 %, first non-empty environment 15.2 %, stone block on a stone counter 4.9 %, this hands scene 20.3 % (all refused); accepted environments 0.0-2.0 %, a pure wood counter 1.9 % (accepted; it was refused by the old measure at 12.4 %). The same image with the product box moved onto the pure wood is accepted, with the hands in the zone it is still refused.
Known limits (unchanged, reported): the zone gate sees only the zone. Lettering, a logo or a competing object OUTSIDE the zone is not detected by a pixel gate (it needs an object or text detector); it is forbidden in the scene request and judged downstream by the critic. A large low-contrast object is detected through its contour, so a limit close to the accepted evidence was chosen on purpose (a false refusal costs one image; a false acceptance puts an object under the product).

## Incident 3: STOPPED_AT_CREATIVE_BRAIN_PLAN (third live attempt, cost EUR 0.0096, 2 text calls, no concept)
Chain: OBSERVE pass, FRAME pass (call 1, `chatcmpl-be46efa1-259a-9042-99b7-e71d1d9ffce9`), IDEATE sent (call 2, `chatcmpl-0a7a7ac9-36e4-9149-8f15-f83e3d6870af`) and answered, then the concept contract refused the answer: `concepts[0].risisks is not part of this contract` (the model misspelled the key `risks`). No concept was normalized, so no distinctness check, no selection call, no art direction, composition, scene or production strategy ran. Cause: **CONCEPT_OUTPUT_INVALID**, in the first round (no round budget consumed beyond it). The Brain's closed contract was right to refuse an unknown key, but a misspelling of one key of a model's answer is not a creative failure, and the run reported only "the plan stopped" and lost the answer. Not a quality-bar rejection: no concept was ever judged.
Fix: (1) an UNAMBIGUOUS near-miss key (exactly one unknown and one missing key, within two edits) is corrected locally and deterministically, with no second model call, and recorded as `key_repairs` evidence in the ledger; every value is still validated, the quality bar is untouched. (2) Every Brain failure names its stage and round (`error.brain_stage`, `error.brain_round`) and keeps the model answer (bounded) as evidence. (3) The runner classifies a stop with one name of a closed list (`failure.js`): PROBLEM_FRAME_INVALID, IDEATION_PROVIDER_FAILURE, CONCEPT_OUTPUT_INVALID, CONCEPTS_NOT_DISTINCT, NO_CONCEPT_MEETS_BAR (a VALID_CREATIVE_BRAIN_REJECTION, the second concept round then starts on its own), CONCEPT_SELECTION_PROVIDER_FAILURE, CONCEPT_SELECTION_INVALID, ART_DIRECTION_PROVIDER_FAILURE, ART_DIRECTION_INVALID, COMPOSITION_PLAN_INVALID, CREATIVE_BRAIN_RUNTIME_WIRING_DEFECT. `final.reason`, `final.stopped_at` and `final.stopped_round` carry it.

## Incident 4: COMPOSITION_PLAN_INVALID at COMPOSE (fourth live attempt, cost EUR 0.0366, 5 text calls, no image)
Chain: OBSERVE, FRAME, IDEATE (3 concepts), SELECT (`cnc_7976a535…` selected, two rejected), ART DIRECT (`art_b57f9a98…`) all passed; COMPOSE (`chatcmpl-3731013f-fd87-9830-9c91-d28d2995c1ca`) answered, and the contract refused the plan: `A_RECEDING_PRODUCT_IS_NOT_STRONG`. The model stated `hero_relationship: PRODUCT_RECEDES_INTO_SCENE` together with `visual_weight.PRODUCT: DOMINANT` (its rationale spoke of "the product grounded in the scene", an art-direction relationship it confused with the composition value). Every other field was valid. Cause: **COMPOSITION_RELATIONS_CONTRADICTORY**. The Brain behaved correctly (the contradiction is real and which side the model meant is a creative choice Nordla must not make for it). Weaknesses found: the instruction named only three of the seven rules the contract enforces and did not define the hero values; the record lost the concept, the art direction and the failed rule (the old record kept ids only).
Fix: (1) the relation rules are now one table (`RELATION_RULES`) that the validator enforces AND the COMPOSE instruction prints, with each value's meaning and the confusion that caused this failure; an independent oracle test checks all 2304 combinations of the constrained relations. (2) The runner records the failed rule (`error.problem`), classifies COMPOSITION_RELATIONS_CONTRADICTORY or COMPOSITION_OUTPUT_INVALID, and keeps the partial plan (`partial_plan`: full concept, art direction, composition if any; `concept_rounds`; `problem_frame`). (3) No second COMPOSE call: the bounded policy (worst case 9 text calls) has no composition retry, and a retry or a coercion of the contradiction would be a creative decision made for the model; recommended for the owner to decide separately: a single violation-aware re-ask.

## Incident 5: ART_DIRECTION_INVALID at ART_DIRECT (fifth live attempt, cost EUR 0.0310, 4 text calls, no image)
Chain: OBSERVE, FRAME, IDEATE (3), SELECT (`cnc_e5ff9249…`, a photo peeling off a screen and curling into a case) passed; ART_DIRECT (`chatcmpl-82b0af04-5c2c-92cb-9321-8100fd81a039`) answered a complete, well-formed art direction and the contract refused ONE element: `narrative_elements[0].element` = "a flat luminous surface suggesting a screen left behind" contains the word `screen` (`SCENE_ELEMENT_SUBSTITUTES_THE_PRODUCT`, a device-like object near the product zone). Everything else in the answer was valid (verified offline). Cause: **ART_DIRECTION_OUTPUT_INVALID**: the rejection is valid, and the instruction had never listed the refused words, nor the length and count limits, nor the exact reason rule (what the model was told: "never describe ... a device"). The selected concept itself needs a screen, a phone and a case in its story (feasibility was judged PARTIAL), so the art director was asked to express an idea whose objects the scene may not carry.
Fix: the forbidden lexicon and the contract limits are data (`SUBSTITUTE_LEXICON`, `ART_LIMITS`) printed by the ART_DIRECT instruction and enforced by the validator from the same constants, with the instruction to express such an object without naming it (light, material, gesture, trace, an empty place); an exact-correspondence test refuses every printed word and checks every limit at its boundary. Found on the way: the lexicon guard now also matches the multi-word entries (`main subject`, `sujet principal`) that never matched before, and the record of a stopped plan now keeps the SELECTED concept as soon as it is selected (it was lost when art direction failed).
No second ART_DIRECT call (bounded policy, no retry). Recommended for the owner, not built: a concept-selection criterion that knows the scene cannot depict devices, so a concept whose idea needs one is judged infeasible before art direction.

## Hardening pass: contract parity (offline, no provider call)

Five live attempts each stopped on one contract/instruction mismatch. The method changed: every model-generated stage now has ONE declarative contract (`src/creative-brain/contract.js`: spec + rules), and the model instruction, the validator, the generators and the audit are all derived from it.

- **Matrix**: `docs/architecture/creative-brain-contract-matrix.md` lists, per stage (FRAME, IDEATE, SELECT_CONCEPT, ART_DIRECT, COMPOSE, execution critic, concept critic; SCENE, PRODUCTION_STRATEGY and recovery are deterministic), every validator rule, the exact instruction text that states it, and the validator source. Regenerate with `node scripts/check-creative-brain-parity.mjs --write-matrix`; a test fails if it is stale.
- **Parity audit** (`src/creative-brain/parity.js`): every validator rule must be stated in the instruction, every instruction rule must be enforced or marked advisory. Drift fails the audit and the gate.
- **One near-miss layer** (`normalizeNearMisses`): only unambiguous syntactic repairs (one misspelled key within 2 edits, whitespace, contract-declared case-insensitivity, empty optional), each journaled as `{path, from, to}`. It never chooses between creative meanings, invents content, or changes an enum.
- **Property/fuzz**: for every contract, generated valid structures are accepted and every single-rule mutation is refused with the precise rule (`test/creative-brain-contract-parity.test.js`).
- **Synthetic end to end** (`test/creative-brain-synthetic-e2e.test.js`): happy path to READY_FOR_OWNER_REVIEW, round 2 after a rejection, RECONCEPT, REFINE, RECOMPOSE, and a malformed answer at each model stage; every stop names stage, round, code, raw-answer evidence, provider calls and cost.
- **Live-readiness gate** (`src/creative-brain-benchmark/readiness.js`): `--check` and `--live` are blocked with `CONTRACT_PARITY_NOT_READY` unless the verdict is `CREATIVE_BRAIN_CONTRACT_PARITY_READY`: parity computed now, plus `docs/architecture/creative-brain-readiness.json` recording the full suite, the mutation sweep, the Node 20 and 24 clean clones and CI for the exact code hash (`node scripts/check-creative-brain-parity.mjs --code-hash`). Any code change invalidates the attestation.

## Incident 7 and the one protocol repair

Attempt 7 stopped at IDEATE: the provider returned text that is not parseable JSON (a bracket closed with the wrong character, a garbled key). That is a protocol failure, not a creative one. A stage may therefore re-ask **once**, and only when the provider call succeeded, a body exists, and parsing failed before any contract validation (`src/creative-brain/model-port.js`, `PROTOCOL_REPAIR`).

- Same stage, same model, same instruction (same input, creative context and contract) plus an addendum asking for the same intended answer as valid JSON, without adding, removing or reconsidering any creative decision. The malformed text is attached as repair evidence only (bounded to 6000 characters).
- Never after a semantic, contract or relation failure; never twice; no new or alternative answer. The repaired text goes through the complete canonical validation and the near-miss layer like any answer.
- Journal (`meta.protocol_repair`, in the Brain ledger and in `error.evidence.protocol_repair`): original request id, malformed response sha256 and length, parse failure, repair request id, outcome (`PARSED`, `STILL_MALFORMED`, `PORT_FAILED`), original and added cost; after a failure the original malformed answer is kept beside the repair answer.
- Bounds: the worst case is now 18 text calls (9 stage calls plus at most one repair per stage call); the Brain port is bounded to 18 and the spend ceiling to EUR 0.95, under the EUR 1.00 hard ceiling.

## Incident 8 post-mortem: PROBLEM_FRAME_INVALID after CONTRACT_PARITY_READY (cost EUR 0.0088, 2 text calls)

- **What happened.** The FRAME instruction listed fields as `answer.audience: ...`. The model wrapped its whole answer in an `"answer"` key (twice: the first answer also had a broken array, which triggered the one protocol repair; the repair came back valid JSON but still wrapped). `frame.answer is not part of this contract` (BRAIN_UNKNOWN_KEY). Unwrapped, the content passed the FRAME contract: the model's framing was sound, the structure was refused for a reason the model was invited to commit.
- **Root cause class: FRAME_CONTRACT_TOO_BRITTLE, caused by an instruction-rendering defect.** The parity pass proved every rule is *stated*; it did not prove the model is *shown the shape* it must emit, and the fuzz generated shape-correct objects and mutated one rule at a time, never a model's structural habits.
- **Fixes (generic, all model stages).** (1) every instruction now shows the exact JSON skeleton, says there is no wrapper key and that dotted names are not keys (`renderShape`; the parity audit fails an instruction without it); (2) a lone wrapper around the whole answer is unwrapped and journaled (`ENVELOPE`) when it is a generic envelope word or when the inside is exactly the contract's object; (3) duplicate keys in one object are refused (JSON.parse silently keeps the last), never re-asked.
- **Not done, recommended.** The provider port sends no `response_format`; compliance is prompt-only plus after-the-fact validation. See the structured-output recommendation in the incident report.

## Generation-time JSON mode (`response_format: json_object`)

Every Creative Brain text call (FRAME, IDEATE, SELECT_CONCEPT, ART_DIRECT, COMPOSE and the protocol-repair re-ask) is sent with `response_format: {"type": "json_object"}` by `createQwenBrainPort`; the vision critics and the Creative Director port are unchanged. The provider requires the word JSON in the prompt, so `createMarketingCopy` refuses a `json_object` call whose system or user text lacks it, before anything is reserved or sent; every stage instruction states JSON. The journal records `response_format`.

`json_object` guarantees syntax only. It is not schema enforcement: the canonical validators, the shared near-miss layer, the semantic and cross-field rules and the single bounded protocol repair are unchanged, and the call and cost bounds did not move (18 text calls, EUR 0.95).

**Follow-up, not done:** `json_schema` strict mode. Before migrating, verify on the Frankfurt endpoint that `qwen3.8-max` supports it, and the exact subset of JSON Schema it accepts (the English and Chinese help pages differ on Max models); then decide.
